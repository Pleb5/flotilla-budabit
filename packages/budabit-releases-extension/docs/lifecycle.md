# Release widget lifecycle

`App.svelte` registers `widget:init`, `context:update`, `context:repoUpdate` and theme listeners before signaling readiness. A revision-guarded `context:getRepo` fallback recovers missed initial messages, including the viewer. Null clears are honored; account, repository and maintainer changes reset list/detail/create navigation. An empty maintainer array never grants arbitrary accounts publication rights.

The authority/list controller is owned by `App.svelte`, not `ReleaseList.svelte`, and remains active across list/detail/create navigation. It registers its event handler synchronously, opens a host-owned subscription and performs bounded historical queries. Disposal on context change or app teardown removes listeners and timers immediately, aborts subsequent query pages, and closes subscriptions even if their creation response arrives after disposal. Discovery retry restarts the controller. The host owns physical subscription cleanup; unsubscribe error payloads are reported rather than mistaken for success.

Cached releases never establish application authority. Live/query revisions use canonical addressable keys, not event IDs. New application revisions can revoke repository linkage. Data omitted from a completed live query is not kept indefinitely as authoritative cached history.

Externally supplied records are independently verified and copied into immutable internal events. Reconciliation reuses only those owned records, not relay verification flags or ID-only caches. Subscription emissions are coalesced over 16 ms; a 250-event backfill regression requires exactly 250 signature checks and one state emission after initial discovery.

Detail follows the selected release coordinate in current authority state. It shows newer revisions, removes stale downloads/verification presentation on revocation, and checks current authority again after delayed asset queries. Detail and creation loaders ignore results after their view is disposed.

Detail samples the authority getter with Svelte `untrack`: it always reads the latest snapshot for the before/after-load checks, but unrelated list emissions do not become dependencies of the asset-loading effect. The effect still depends on the selected release, repository/bridge and explicit retry; App's selected-coordinate reconciliation still handles replacement/revocation. An unrelated release/application update preserves the file input and any in-progress hash check without querying assets again. Intended reloads clear obsolete verification statuses as well as generation tokens, so an explicit retry cannot leave a canceled check stuck at “Checking…”.

Publication checks a pinned account/repo before each step and re-discovers application authority before **every batch attempt**, including same-session resume. Embedded application events are reconciled with live revisions, never treated as a replacement for discovery. A revocation that occurs after this preflight may still race sequential remote writes; there is no atomic relay transaction or global latestness guarantee. Leaving or changing the context stops subsequent work; already-running host signing/publishing may still complete.

The saved signed batch is the recovery point, not an assumption of atomic publication. Each new batch has a unique identity and must atomically claim an empty repository/account slot. Before publishing, at each progress save and on completion, the widget compares the exact observed storage revision under the host's cross-tab lock. Corrupt or no-longer-authorized journals expose retry and confirmed local discard only when their revision is pinned; cancellation/storage failure leaves data intact. Discard clears only that reviewed revision. A stale creator, publisher or discard confirmation reports a conflict and reloads current recovery state, clearing stale confirmation and requiring a new user action. A later batch is never automatically published or discarded on behalf of a stale action. See [storage](storage.md) for legacy journal handling, host requirements and limits; local deletion cannot undo published events.

The actual Budabit repo-tab uses readiness plus context updates, not a guaranteed `widget:mounted`/`widget:unmounting` sequence. Its bridge is detached/recreated when the widget identity, permissions, URL or repository changes. It resends init/context/theme after an accepted readiness message or first message from an accepted runtime origin.
